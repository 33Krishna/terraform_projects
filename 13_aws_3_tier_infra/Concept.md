## 1. Why 3-Tier Architecture?

**Q: Monolithic ke bajaaye 3-tier kyun?**

Each tier independently scale hoti hai. Agar sirf backend pe load hai toh sirf backend ASG scale karo — frontend aur DB ko touch nahi karna padta. Security bhi better hai — DB directly internet se accessible nahi. Aur separation of concerns — frontend change karo bina backend touch kiye.

**Tiers breakdown:**

| Tier | Layer | Technology | Subnet Type |
|------|-------|------------|-------------|
| Tier 1 | Presentation | Node.js (Port 3000) | Private |
| Tier 2 | Logic/API | Go Backend (Port 8080) | Private |
| Tier 3 | Data | PostgreSQL RDS (Port 5432) | Isolated |

## 2. ALB — External vs Internal

**Q: Tumhare project mein 2 load balancers kyun hain?**

- **External ALB** — internet-facing hai, users ka traffic receive karta hai aur frontend instances pe route karta hai.
- **Internal ALB** — sirf VPC ke andar kaam karta hai, frontend EC2 se backend EC2 tak traffic route karta hai.

Isse backend directly internet pe expose nahi hota. Agar frontend ka private IP hardcode karte toh ASG scaling pe woh IP change ho jaata — internal ALB us problem solve karta hai.

**Traffic Flow:**
```
Internet → External ALB → Frontend EC2 (Port 3000)
                              ↓
                       Internal ALB → Backend EC2 (Port 8080)
                                           ↓
                                    RDS PostgreSQL (Port 5432)
```

## 3. Auto Scaling Group (ASG)

**Q: ASG kaise kaam karta hai? Scaling trigger kya hai?**

ASG ek min/desired/max configuration maintain karta hai. Jab CPU 70% cross karta hai, CloudWatch alarm fire hoti hai aur ASG ek naya instance launch karta hai.

| Config | Frontend ASG | Backend ASG |
|--------|-------------|-------------|
| Min | 2 | 2 |
| Desired | 2 | 2 |
| Max | 4 | 6 |
| Scale-Out Trigger | CPU > 70% | CPU > 70% |
| Scale-In Trigger | CPU < 30% | CPU < 30% |
| Cooldown | 300 seconds | 300 seconds |

> **Why backend max is 6 vs frontend max 4?** Backend handles DB queries, business logic — zyada compute-intensive hota hai, isliye max zyada rakha.

## 4. Secrets Manager

**Q: DB password environment variable mein directly kyun nahi rakha?**

Plain text password EC2 user data mein hoti toh AWS Console se visible hoti — security risk. Secrets Manager mein store kiya, backend EC2 ko IAM role ke through read access diya.

**Access Pattern:**
```
Backend User Data Script
    → aws secretsmanager get-secret-value
    → JSON parse (username, password, host, port, dbname)
    → Docker run --env DB_HOST=... --env DB_PASS=...
```

**Stored Secret Structure:**
```json
{
  "username": "postgres",
  "password": "<auto-generated-32-char>",
  "engine": "postgres",
  "host": "dev-goal-tracker-postgres.xxx.rds.amazonaws.com",
  "port": 5432,
  "dbname": "goalsdb"
}
```

> **Bonus:** Secrets Manager automatic rotation bhi support karta hai — password periodically rotate hota hai bina manual intervention ke.

## 5. VPC & Subnet Design

**Q: 8 subnets kyun? Sab same kaam nahi kar sakti thein?**

Har tier ka alag security requirement hai:

| Subnet Type | CIDR | Contains | Internet Access |
|-------------|------|----------|----------------|
| Public (AZ-a) | 10.0.1.0/24 | ALB, NAT Gateway, Bastion | Yes (IGW) |
| Public (AZ-b) | 10.0.2.0/24 | ALB, NAT Gateway | Yes (IGW) |
| Frontend Private (AZ-a) | 10.0.11.0/24 | Frontend EC2s | Outbound via NAT |
| Frontend Private (AZ-b) | 10.0.12.0/24 | Frontend EC2s | Outbound via NAT |
| Backend Private (AZ-a) | 10.0.21.0/24 | Backend EC2s | Outbound via NAT |
| Backend Private (AZ-b) | 10.0.22.0/24 | Backend EC2s | Outbound via NAT |
| DB Isolated (AZ-a) | 10.0.31.0/24 | RDS Primary | None |
| DB Isolated (AZ-b) | 10.0.32.0/24 | RDS Standby | None |

> Agar sab ek subnet mein hote toh ek breach pe poora system exposed. Defense-in-depth principle.

## 6. Security Groups — Least Privilege

**Q: Security groups kaise configure kiye?**

Chain-based access — har SG sirf apne ek upar wali layer se traffic accept karta hai:

```
0.0.0.0/0 → ALB SG (80/443)
ALB SG    → Frontend SG (3000)
Frontend SG → Backend SG (8080)
Backend SG → RDS SG (5432)

Your IP → Bastion SG (22)
Bastion SG → Frontend/Backend SG (22)
```

> Yeh defense-in-depth hai — ek layer breach ho toh bhi next layer protected hai. RDS SG mein koi bhi direct source IP allow nahi — sirf Backend Security Group reference hai.

## 7. NAT Gateway

**Q: Private subnets ko NAT Gateway kyun chahiye?**

Private EC2s ko outbound internet chahiye:
- Docker Hub se image pull karna
- AWS APIs call karna (Secrets Manager, CloudWatch)
- OS package updates

NAT Gateway public subnet mein hota hai with Elastic IP. Private instances ka traffic NAT se bahar jaata hai, response wapas aata hai — **lekin koi bhi internet se directly private instance reach nahi kar sakta.**

**Dev vs Prod setting:**
```hcl
single_nat_gateway = true   # Dev: cost save (~$32/month saved)
single_nat_gateway = false  # Prod: HA — har AZ mein alag NAT Gateway
```

> `false` karne se agar AZ-a ka NAT fail ho toh AZ-b ke instances unaffected rahenge.

## 8. Bastion Host vs SSM

**Q: SSM hone ke baad bhi Bastion kyun?**

| Feature | Bastion Host | SSM Session Manager |
|---------|-------------|---------------------|
| Port 22 open | Yes | No |
| SSH key required | Yes | No |
| Audit trail | Manual | CloudTrail automatic |
| SCP / tunneling | Yes | Limited |
| Browser access | No | Yes (Console) |
| Cost | EC2 cost | Free |

Dono options available rakhe. Production mein SSM prefer karte hain — no open port 22, full audit trail. Bastion backup option hai aur kuch tools ke liye useful.

## 9. Docker + EC2 User Data

**Q: ECS nahi use kiya, directly EC2 pe Docker kyun?**

Yeh learning aur cost tradeoff tha. ECS Fargate zyada managed hai lekin concepts hide ho jaate hain. EC2 pe Docker directly — user data script mein:

```bash
# User Data Script Flow
1. Install Docker & AWS CLI
2. Login to Docker Hub (credentials from tfvars)
3. Pull image: docker pull username/goal-tracker-backend:latest
4. Get secrets: aws secretsmanager get-secret-value
5. Parse JSON with jq
6. Run container: docker run -d -p 8080:8080 --env DB_HOST=... image
7. Setup CloudWatch log agent
```

> **Production mein:** ECS Fargate ya EKS prefer karenge — rolling deployments, task definitions, service mesh sab managed hota hai.

## 10. Multi-AZ Design

**Q: Multi-AZ ka real benefit kya hai?**

AWS ka ek AZ ek isolated data center hai — alag power, cooling, network. AZ-a fail ho jaye — AZ-b ke instances serve karte rahen.

**RDS Multi-AZ:**
- Synchronous replication — primary write hota hai, standby simultaneously update hota hai
- Automatic failover: ~1-2 minutes downtime
- Same region mein protection (disaster recovery ke liye Cross-Region Replication alag hai)

**ALB behavior:**
- Automatically unhealthy instances ko traffic route karna band
- Health check fail ho → instance deregister → new instance launch (ASG)

> **HA vs DR difference:** Multi-AZ = same region mein high availability. Cross-region replication = disaster recovery (different region).

## 11. Terraform Modules

**Q: Sab kuch ek file mein kyun nahi likha?**

| Module | Responsibility |
|--------|---------------|
| `vpc` | VPC, 8 subnets, route tables, IGW |
| `alb` | External + Internal load balancers, target groups |
| `bastion` | Jump box EC2, EIP |
| `frontend-asg` | Launch template, ASG, scaling policies |
| `backend-asg` | Same for backend |
| `rds` | PostgreSQL instance, subnet group, parameter group |
| `iam` | EC2 instance role, policies |
| `secrets` | Secrets Manager secret, IAM policy |
| `security_groups` | All SGs with chain-based rules |

**Benefits:**
- **Reusability** — staging environment mein same modules, different vars
- **Isolation** — RDS issue hai toh `terraform plan -target=module.rds`
- **Readability** — `main.tf` sirf module calls hai, 50 lines mein poora infra
- **Testing** — individual modules independently test kar sakte hain

## 12. RDS vs Self-Managed DB

**Q: EC2 pe PostgreSQL install karne ke bajaaye RDS kyun?**

| Feature | RDS | EC2 Self-Managed |
|---------|-----|-----------------|
| Automated backups | Yes (7 days) | Manual scripts |
| OS patching | AWS handles | Manual |
| Multi-AZ failover | Built-in | Complex setup |
| Encryption at rest | One checkbox | Manual config |
| CloudWatch integration | Automatic | Manual agent |
| Storage auto-scaling | Supported | Manual resize |
| Cost | Higher | Lower |

> **RDS tradeoff:** ~30-40% costlier than EC2 self-managed, lekin operational overhead kaafi kam. Dev/startup ke liye RDS almost always better choice.

## 13. IAM Roles & Least Privilege

**Q: EC2 ko kaun si permissions di aur kyun?**

```
EC2 Instance Role
├── AmazonEC2ContainerRegistryReadOnly
│   └── ECR se Docker images pull karna
│
├── AmazonSSMManagedInstanceCore
│   └── SSH key ke bina SSM Session Manager access
│
├── CloudWatchAgentServerPolicy
│   └── Logs aur metrics CloudWatch ko bhejana
│
└── Custom Secrets Manager Policy
    └── Sirf specific secret ARN pe GetSecretValue
        (poore account ka access nahi — least privilege)
```

**Q: IAM Role vs IAM User EC2 ke liye?**

IAM Role temporary credentials use karta hai (STS) — rotate nahi karna padta, expire automatically hota hai. IAM User ka access key permanent hota hai — leaked ho gaya toh manually rotate karna padta hai. EC2 ke liye hamesha Role use karo.

## 14. CloudWatch — Logs, Metrics, Alarms

**Q: CloudWatch mein kya monitor kar rahe ho?**

**Logs:**
```
/aws/ec2/dev-goal-tracker/frontend   → Application logs
/aws/ec2/dev-goal-tracker/backend    → API logs, DB connection logs
/aws/rds/instance/.../postgresql     → DB query logs, errors
```

**Key Metrics Monitored:**

| Resource | Metrics |
|----------|---------|
| EC2 | CPU, Memory, Disk, Network |
| ASG | Instance count, scaling events |
| ALB | Request count, latency, 4xx/5xx error rate |
| RDS | CPU, connections, ReadIOPS, WriteIOPS, FreeStorageSpace |

**Alarms:**
- Frontend/Backend CPU > 80% → SNS notification
- ALB unhealthy host count > 0
- RDS FreeStorageSpace < 5GB
- ASG scaling events

## 15. Health Checks — ELB vs EC2 Type

**Q: Frontend ASG mein `ELB` health check type hai, Backend mein `EC2` — kyun alag?**

| Type | Checks | When to Use |
|------|--------|-------------|
| EC2 | Sirf instance running/stopped hai | Basic — OS level |
| ELB | ALB actually HTTP request karta hai app ko | Application level |

Frontend ALB se connected hai — ELB health check ALB ki target group se `/` pe GET request karta hai. Agar app crash ho gaya lekin instance chal raha hai, ELB type pakad lega, EC2 type nahi.

Backend internally communicate karta hai aur uske liye Internal ALB ke target group se health check hota hai.

> **Best practice:** Jab bhi ALB connected ho, ELB health check use karo — zyada accurate hai.

## 16. Terraform State Management

**Q: Terraform state kahan store hai? Production mein kya karoge?**

**Current (Dev):** Local `terraform.tfstate` file

**Problem with local state:**
- Team mein koi aur `terraform apply` kare — conflict
- File delete ho jaye — AWS resources orphan ho jayenge
- No locking — 2 log simultaneously apply kare — corruption

**Production Setup:**
```hcl
# backend.tf
terraform {
  backend "s3" {
    bucket         = "my-terraform-state-bucket"
    key            = "dev/goal-tracker/terraform.tfstate"
    region         = "us-east-1"
    encrypt        = true
    dynamodb_table = "terraform-state-lock"  # Locking
  }
}
```

- **S3** — state store karna (versioning enable karo)
- **DynamoDB** — state locking (ek time pe sirf ek apply)
- **Encryption** — state mein sensitive data hota hai

## 17. ECR vs Docker Hub

**Q: AWS ECR ki jagah Docker Hub kyun use kiya?**

| Feature | Docker Hub | AWS ECR |
|---------|-----------|---------|
| Cost | Free (public) / paid (private) | Pay per GB stored + transfer |
| IAM Integration | No | Yes (seamless with EC2 role) |
| Latency | Internet pull | Same region — faster |
| Security | External | Private, VPC endpoint possible |
| Setup | Simpler | Slightly more Terraform code |

Dev environment ke liye Docker Hub simple tha. Production mein ECR prefer karenge:
- IAM role se automatically authenticate — no credentials in user data
- Same region pull — faster deployment
- No external dependency

## 18. Cost Optimization Decisions

**Q: Dev environment mein cost kaise optimize kiya?**

| Decision | Dev Setting | Prod Setting | Monthly Saving |
|----------|------------|-------------|----------------|
| NAT Gateway | `single_nat_gateway = true` | false (2 NATs) | ~$32 |
| RDS Multi-AZ | `db_multi_az = false` | true | ~$25 |
| Instance type | t3.micro | t3.small/medium | Varies |
| RDS storage | 20GB gp3 | Auto-scaling | Varies |

> **gp3 vs gp2:** gp3 ~20% cheaper aur IOPS independently set kar sakte ho — same IOPS ke liye gp2 mein zyada storage buy karna padta tha.

## 19. What Would You Improve in Production?

**Q: Yeh project production-ready banane ke liye kya karoge?**

1. **HTTPS/SSL** — ACM certificate + ALB HTTPS listener (Port 443)
2. **Custom Domain** — Route53 hosted zone + ALB DNS record
3. **WAF** — AWS WAF ALB pe attach karo (SQL injection, XSS protection)
4. **ECR instead of Docker Hub** — Private registry, IAM-based auth
5. **S3 + DynamoDB** — Remote Terraform state with locking
6. **Multi-AZ RDS** — `db_multi_az = true`
7. **2 NAT Gateways** — `single_nat_gateway = false`
8. **ECS/EKS** — EC2 pe manual Docker ke bajaaye managed container orchestration
9. **CI/CD Pipeline** — GitHub Actions: code push → image build → ECR push → instance refresh
10. **VPC Endpoints** — Secrets Manager, S3, ECR ke liye — traffic AWS network pe rahe, NAT se na jaaye
11. **CloudTrail** — API calls audit karna
12. **GuardDuty** — Threat detection

## Architecture Summary (Interview Mein Bolne Ke Liye)

> *"Maine ek 3-tier Goal Tracker app ka AWS infrastructure Terraform se banaya. Node.js frontend aur Go backend alag private subnets mein ASG ke saath deploy hai — frontend 2-4 instances, backend 2-6 instances — CPU 70% pe scale hota hai. External ALB internet traffic handle karta hai, Internal ALB frontend-to-backend communication ke liye. RDS PostgreSQL isolated subnets mein hai — koi direct internet access nahi, sirf backend security group se reachable. Secrets Manager se DB credentials runtime pe inject hote hain — plain text kahi nahi hai. Poora setup multi-AZ hai, Terraform modules se IaC ke through deploy kiya, CloudWatch se monitoring hai. Dev mein cost optimize kiya — single NAT, single AZ RDS. Production ke liye HTTPS, WAF, ECR, remote state, aur CI/CD add karunga."*
